# NN-Accelerator

An INT8 neural-network accelerator in synthesizable SystemVerilog, verified
against a Python/NumPy golden model. It runs a two-layer fully connected
network (16 → 32 → 10) entirely in simulation, with the number of parallel
multipliers as a parameter.

Everything here is simulation. There are no frequency, power, LUT or DSP
numbers anywhere in this repository, because nothing has been through a
synthesis tool and those would not be measurements.

```
        INT8                                                      INT32
   X ──────────▶┌───────────────┐    INT8     ┌───────────────┐──────────▶ logits
                │   layer 1     │  requant    │   layer 2     │
   W1,W2 ──────▶│  16 → 32      │────────────▶│  32 → 10      │
   (resident)   │  + bias, ReLU │  >>8, sat   │  + bias       │
                └───────────────┘             └───────────────┘
                   NUM_MACS MACs                 NUM_MACS MACs
```

**Measured**, 16-32-10, at one and thirty-two MACs (simulated cycles):

| | 1 MAC | 32 MACs |
|---|---:|---:|
| Weight load, paid once | 834 | 834 |
| Cycles per inference, host waits for `done` | 893 | 109 |
| Cycles per inference, host keeps input fed | **860** | **76** |
| MAC utilization | 96.7% | 34.2% |

832 multiply-accumulates per inference. Full sweep in
[docs/PERFORMANCE.md](docs/PERFORMANCE.md), regenerated by `make perf`.

## Why INT8

Inference does not need float. An INT8 weight and an INT8 activation multiply
into exactly 16 bits, and a few hundred of those accumulate comfortably in 32,
so the arithmetic is exact — no rounding anywhere in the datapath. That matters
for verification as much as for hardware: the RTL and a NumPy model can be
compared for **bit-exact equality** rather than within a tolerance, so any
mismatch is a real bug rather than a floating-point artefact.

In hardware an 8×8 multiplier is far smaller than a float unit, so the same
area buys more of them, which is the point of the `NUM_MACS` parameter.

The cost is dynamic range, and it shows up in one place: between the layers.
Layer 1 accumulates in INT32, but layer 2's multiplier takes INT8, so the
activations have to come back down. That is the requantizer, and it is the only
lossy step in the design.

## Architecture

Datapath and control are separate throughout. The largest RTL file is 219 lines.

```
  rtl/nn_accelerator.sv        two layers + requantizer, and weight-load routing
    ├── rtl/nn_layer.sv        Y = ReLU(X·W + B)   (one per layer)
    │     ├── rtl/matrix_mult.sv     streaming datapath: operand memory + MAC array
    │     │     ├── rtl/matmul_ctrl.sv   the FSM and all counters  (control)
    │     │     ├── rtl/mac.sv           signed multiply-accumulate (×NUM_MACS)
    │     │     └── rtl/matmul_pkg.sv    the state enum
    │     └── rtl/relu.sv            combinational max(0, x)
    └── rtl/requant.sv         INT32 → INT8: arithmetic shift, then saturate
```

952 lines of RTL, 4,589 lines of testbench, 1,127 lines of Python.

Everything is parameterized — dimensions, data width, accumulator width,
requantization shift, MAC count — and no module hardcodes a matrix size. The
testbenches run at several shapes to keep that honest.

**Streaming interface.** Every block uses the same AXI-Stream-style valid/ready
handshake: a beat transfers on a rising edge where both are high. `s_ready` and
`m_valid` are decoded from the registered state only (Moore), so `s_ready`
never depends combinationally on `s_valid` and `m_valid` never on `m_ready`. No
combinational loops, and a stalled cycle costs exactly one cycle — which the
testbenches check cycle by cycle under random stalls.

## The MAC

```
   a ──▶┌───┐
        │ × │──▶ product ──▶ sign-extend ──▶┌───┐
   b ──▶└───┘    (2W bits)      (to ACC)    │ + │──▶┌─────┐──▶ acc
                                            └───┘   │ reg │
                                              ▲     └─────┘
                                     feedback │        │
                                    (0 when clear) ◀───┘
```

`rtl/mac.sv`, parameterized on `DATA_WIDTH` and `ACC_WIDTH`.

**Signedness is explicit everywhere**: both operands are size-cast to the full
product width before multiplying, and because a size cast preserves
signedness, that sign-extends and the multiply is a signed multiply. Getting
this wrong is the classic INT8 bug — `-1 × -1` quietly becoming 65025 — so the
cast is deliberate rather than incidental.

**`clear` asserted together with `en` loads the product directly** instead of
adding it to a stale accumulator, so consecutive dot products need no idle
cycle between them.

The accumulator cannot overflow for any realistic dot product: a W×W signed
product fits in 2W bits, and no sum of up to 2^(N−2W+1)−1 products can wrap,
which is 131,071 terms for INT8 into INT32. The testbench checks that bound
directly rather than taking the arithmetic on trust.

## Matrix multiplication

`rtl/matrix_mult.sv` computes C = A·B one element at a time, streaming.

```
   s_data ──▶ operand memory ──▶ A[i][k] broadcast ──▶ MAC 0 ─┐
              (A region,            ▲                  MAC 1 ─┤ mux
               B region)            │                   ...   ─┤(wb_sel) ──▶ m_data
                                B[k][j_base+p]         MAC P-1─┘
```

One memory holds both operands: A in the low region, B above it. There is no C
buffer — each element streams straight out of the MAC's accumulator the cycle
after it finishes.

The addressing is written out explicitly (`a_addr = i*K + k`) rather than
hidden behind a helper, because a swapped index is easy to write and hard to
see. The testbenches use an index pattern of distinct values to catch it.

## Control FSM

`rtl/matmul_ctrl.sv`. Five states, one job at a time.

```
            s_valid        last A beat (inference)            k == K-1
  ┌──────┐ ───────▶ ┌──────┐ ─────────────────────▶ ┌─────────┐ ──────▶ ┌───────────┐
  │ IDLE │          │ LOAD │                        │ COMPUTE │         │ WRITEBACK │
  └──────┘          └──────┘                        └─────────┘ ◀────── └───────────┘
      ▲                 │                                      m_ready,        │
      │                 │ last B beat (weight load)            more left       │ m_ready,
      │                 ▼                                                      │ last element
      │             ┌──────┐                                                   │
      └─────────────│ DONE │◀──────────────────────────────────────────────────┘
                    └──────┘
```

A job is either a **weight load** (K·N beats into the B region, then straight
to DONE, no output) or an **inference** (M·K beats of A, then compute and
stream out). `load_weights`, sampled with the first beat, decides which, and
selects the operand-memory region the load writes.

All outputs are decoded from the registered state and counters. The encoding is
fixed in `rtl/matmul_pkg.sv` (IDLE=0 … DONE=4) so the state reads as a number
in a waveform. IDLE deliberately does not accept data, so LOAD is the only
state that writes operands; that costs one cycle per job and removes a class of
"did this beat land?" ambiguity.

## Parallelism

`NUM_MACS` output columns are computed at once. Every MAC sees the same
activation `A[i][k]`; MAC *p* reads its own weight `B[k][j_base + p]` and keeps
its own accumulator. A group takes K cycles whatever its width, then streams
out one column per cycle:

```
compute + write-back cycles = M · ceil(N / NUM_MACS) · K + M · N
```

`NUM_MACS = 1` is exactly the original single-MAC schedule. When N is not a
multiple of `NUM_MACS` the last group is short: the spare MACs repeat the last
column so their addresses stay in range, and their results are never streamed
out. That tail case passes at 8×8×8 — where N divides evenly by four — and
fails at 3×16×5, which is why the non-square shape is in the regression.

The write-back term `M·N` does not shrink with `NUM_MACS`. That is the floor
the utilization numbers run into.

## Pipelining and weight reuse

**Weights stay resident.** Originally every inference re-streamed its weights
at one byte per cycle, which capped any benefit from more multipliers at
1.83×. Splitting jobs into weight loads and inferences means the weights are
paid for once: a run of *n* inferences costs 834 + 860·*n* cycles at one MAC
instead of 1,725·*n*. That moved the ceiling from 1.83× to 11.3×.

**The two layers overlap.** Layer 2 consumes each activation in the cycle layer
1 produces it. Measured at one MAC, the layers cost 561 and 363 cycles
standalone but 892 together — exactly HIDDEN_SIZE = 32 cycles saved.

**Inferences overlap, but only partly.** Layer 1 is a separate FSM, so it can
start the next X while layer 2 is still computing. It runs ahead only until its
own first write-back, because there is no buffer between the layers, so it then
stalls until layer 2 returns to LOAD. The gain is a steady 33 cycles at every
width: 3.7% of 893 at one MAC, but 30% of 109 at thirty-two, where it is enough
to reach the slower layer's own period and keep layer 1 busy continuously.

The hazards — one activation buffer per layer, one layer active at a time, one
output beat per cycle, the accumulator read-modify-write, the activation
handoff, and weight coherence being the host's responsibility — are set out in
[ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Verification

The rule: **nothing is claimed to work until the test has been run.** Three
independent things have to agree, on two simulators.

```
   python/golden_model.py            tb/*_tb.sv                tb/*_vec_tb.sv
   (NumPy reference, with            (self-checking,           (vector-driven,
    its own self-test)                models timing)            Python-generated)
          └──────────────────────────────┴─────────────────────────┘
                                         │
                 the same RTL, on Verilator 5.052 and Icarus Verilog 13.0
```

**Self-checking testbenches**, one per module, generate their own stimulus and
check timing as well as values: exact busy-cycle counts under random stalls,
protocol rules on every clock edge, resets from every state, and coverage bins
that *fail the run* if a case is never exercised. ReLU and the requantizer are
checked exhaustively over their whole input space. The controller's testbench
models the FSM transition table and compares state and every counter after each
clock edge.

**A Python-driven regression** inverts the arrangement: NumPy generates the
vectors, the RTL consumes them, NumPy checks what comes back, and the whole
thing exits nonzero on any mismatch, protocol error or deadlock.

Both simulators earn their place. Icarus has caught a forward reference and a
string-literal padding bug that Verilator accepts; Verilator's random reset
initialization (`--x-initial unique`) catches missing resets that Icarus's
convenient zeros would hide. For each shape the two results files are
byte-identical.

**Mutation testing** answers the question a passing suite cannot: 68 deliberate
bugs were injected across the phases and 66 were caught. Both survivors are
documented in [VERIFICATION.md](docs/VERIFICATION.md) — one is genuinely
unreachable at the network level, and is why the unit testbenches still exist.

## The Python golden model

`python/golden_model.py` is the reference, in about 200 lines of NumPy. It is
deliberately **not** a second implementation of the hardware: it is the
arithmetic definition of what the hardware should compute, written the obvious
way. `matmul_int8`, `relu_int32`, `layer_affine`, `layer_relu`, `requantize`,
`network_2layer` — each a few lines, each mirroring one hardware block.

It is checked against plain Python before it is trusted to judge anything
(`make golden`): 72 matrix cases, 56 layer cases and 30 network cases across
four shift values, plus hand-computed values and range checks.

The RTL computes; Python only predicts and compares. One subtlety worth
recording: the requantizer's arithmetic right shift floors toward negative
infinity rather than truncating toward zero, so NumPy's `>>` matches the
hardware exactly. Getting that backwards would have produced off-by-one logits
on negative values only.

## Results

All simulated cycle counts. No clock frequency is implied.

**Per inference, 16-32-10** (`make perf`):

| MACs | Weight load | Latency | Interval, waits for `done` | Interval, input kept fed | Utilization | Speedup |
|-----:|------------:|--------:|---------------------------:|-------------------------:|------------:|--------:|
| 1 | 834 | 892 | 893 | **860** | 96.7% | 1.00× |
| 4 | 834 | 284 | 285 | **252** | 82.5% | 3.41× |
| 8 | 834 | 188 | 189 | **156** | 66.7% | 5.51× |
| 16 | 834 | 124 | 125 | **92** | 56.5% | 9.35× |
| 32 | 834 | 108 | 109 | **76** | 34.2% | 11.32× |

Utilization falling from 96.7% to 34.2% is the real result. The input load, the
activation handoff and the output beats do not shrink with `NUM_MACS`, and the
output layer has only 10 columns, so above 10 MACs some of its multipliers have
nothing to do. At 32 MACs the interval has reached the slower layer's own period
of 76 cycles and more multipliers would buy nothing.

**Verification**, from a clean tree, 0 errors on both simulators:

| | Verilator | Icarus |
|---|---|---|
| Testbench runs | 28 | 22 |
| Values recomputed with NumPy, testbench flow | 53,531 | 53,531 |
| Vector-driven cases | 2,025 | 2,025 |
| Values recomputed with NumPy, regression flow | 74,790 | 74,790 |

## Limitations

- **Simulation only.** Nothing has been synthesized. No frequency, power, LUT,
  DSP or wall-clock figures, and the speedups are ratios of simulated cycle
  counts, not of real time.
- **No formal verification**, no equivalence checking, no gate-level or
  post-synthesis simulation.
- **The operand memory is registers**, one write port and `NUM_MACS + 1` read
  ports. Fine in simulation and for LUT storage; block RAM would need banking.
- **One activation buffer per layer**, so inferences only partly overlap.
- **The weight port is one byte per cycle.** The 834-cycle load is unchanged at
  every MAC width.
- **Weight coherence is the host's job.** Nothing records whether weights were
  ever loaded; reset leaves the operand memory untouched.
- **Fully connected layers only.** No convolution, no attention, no batching,
  and 16-32-10 is far smaller than anything useful.
- **Mutation testing is not automated**, so those numbers are a record of runs
  rather than something CI reproduces.
- **The older testbenches are not lint-clean** under `verilator -Wall`.

## If this went to an FPGA

Not done, and deliberately not estimated. What it would take, in order:

1. **Synthesize and find the real critical path.** The likely candidate is the
   combinational chain from the MAC accumulator through bias add, ReLU and
   requantization to the output port. If it misses timing, that chain wants a
   pipeline register — a cycle of latency, nothing in throughput.
2. **Move the operand memory to block RAM.** The register array with
   `NUM_MACS + 1` read ports will not map as written; it needs banking so each
   MAC reads its own bank, or a different schedule.
3. **Replace the MAC array with DSP primitives** if the target has them, while
   keeping the generic `rtl/mac.sv` so the design stays portable. The RTL
   avoids vendor primitives today for exactly this reason.
4. **Add a real host interface.** The streaming interface is AXI-Stream in
   shape but not in name; it would need proper AXI4-Stream plus AXI4-Lite
   control.
5. **Then measure.** Only after all of that would frequency, LUT, DSP and power
   numbers mean anything, and only then would a speedup claim against a CPU be
   defensible.

The architectural change with the clearest payoff is double-buffering the
activations, because the measurements already show what it would buy: the
interval would fall towards the slower layer's own period at every width, not
just at thirty-two MACs.

## Building and running

macOS, Apple Silicon:

```sh
brew install verilator        # primary simulator (5.x, needs Xcode CLT for C++)
brew install icarus-verilog   # secondary simulator for cross-checking
brew install surfer           # waveform viewer
brew install lz4              # only needed for FST waveforms
make venv                     # .venv with numpy (Homebrew Python blocks global pip)
make check-tools              # report what is installed
```

```sh
make test            # Verilator: lint, golden model, every testbench, NumPy checks
make test-iverilog   # the same on Icarus Verilog
make regression      # 1,000 randomized Python-generated cases per DUT
make perf            # performance sweep, rewrites docs/PERFORMANCE.md
make waves           # waveforms for every testbench
make help            # every target
```

Individual blocks: `make mac`, `relu`, `requant`, `ctrl`, `matmul`, `layer`,
`net`, each with `-params`, `-iverilog` and `-waves` variants.
